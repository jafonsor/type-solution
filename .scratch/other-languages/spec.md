# Spec: Other Languages for Solutions, PureScript first

Status: ready-for-agent

Map: [map.md](map.md). Every decision below comes from the map's resolved tickets, linked where they hold more detail. Terms (Language, Solution, Reference Solution, Personal best, Peek) are defined in `CONTEXT.md`. This spec changes the MVP spec ([../type-solution/spec.md](../type-solution/spec.md)); where they disagree, this one wins, and ADR 0002 (below) records that.

## Design Contract

Rules every build decision must keep. Breaking one means stopping to ask.

- **L1 — No server.** The deploy stays static (GitHub Pages). Typed code never leaves the browser, for every Language. A Language that needs a server is out of scope. ([ticket 06](issues/06-grilling-checking-without-browser-compiler.md))
- **L2 — Tests are Language-neutral.** A Puzzle has one set of tests, `args` and `expected` as JSON, shared by every Language.
- **L3 — One Run, many Languages.** The player may switch Language mid-Run. Switching does not reset the clock; whichever Solution passes first ends the Run.
- **L4 — A Language ships only when complete.** Every Puzzle in the bank has a Reference Solution and signature in it. A Puzzle written later must arrive with one in every shipped Language.
- **L5 — The seams stay narrow.** Adding a Language touches only its four seams (below) and its `languages/<name>/` folder. Not the dropdown, saved data, Run, Personal best or Puzzle file format.
- **L6 — The MVP contract otherwise holds.** I1 to I6 and I8 of the MVP spec stand. I7 ("JavaScript only") is superseded by this spec. I2's "no suggestions or autocomplete" gets one exception: the import popup (see Editor).

## Player behaviour (Language-neutral)

All of this is the same for every Language.

**Choosing a Language**
- A dropdown at the right edge of a thin bar directly under the editor (like VS Code's status bar picker). **Alt+L** cycles Languages from inside the editor. Tabs above the editor and a dropdown by the signature were rejected. ([ticket 05](issues/05-prototype-language-dropdown.md), prototype in `prototype-language-dropdown/`)
- The choice is remembered in this browser; a new Puzzle opens in the last Language chosen. First visit, or an unknown saved value: JavaScript.
  - **As built (ticket 29):** the bar's dropdown is built from the Language registry (`static/editor/src/languages.mjs`), so a Language added there appears with no other change. Each Language's draft is a whole editor state (text, cursor, undo history) kept in memory; a new Run (either menu button) drops every draft and keeps the Language. The `type-solution.language` key is read once at page load and written on every pick. The `?` is built in ticket 30 (see "As built (ticket 30)" under Peeking).
- The bar also holds a hoverable `?` that shows the Reference Solution as a tooltip ([ADR 0001](../../docs/adr/0001-reference-solution-shown-on-hover.md)).

**Drafts.** Each Language keeps its own draft during a Run; switching shows that Language's draft. An untouched Language opens empty (no pre-fill, not even the signature as code). Drafts live in memory only; a reload starts a fresh Run.

**The Run and its credit** ([map Notes](map.md))
- The clock starts at the first keystroke (in any Language), as today. A Run that switched is slower by that much; there is no reset.
- The Run belongs to the Language that passed. Words per minute and Backspace count are the passing Solution's; the time is the whole Run.
- **Personal best** is per Puzzle and Language. A Run that switched is still eligible, with its whole-Run time.
- **Key presses** count toward the Language they were typed in; Most missed and Slowest lists are per Language.
- The Run's time ends when the passing check's result arrives, so waiting for a compiler counts. Preloading keeps that wait small.

**Peeking** ([ticket 15](issues/15-grilling-peeking-at-the-solution.md)). Tooltip open for about 1 s or more, in any Language, marks the whole Run "peeked". It stays eligible for the Personal best; the plain word "peeked" shows wherever the time is shown (end-of-Run result, beside the best on the status line, in lists). A faster Run replaces the best, peeked or not; the mark follows the Run that holds the best; a slower unpeeked Run does not replace a faster peeked best. The Run record carries a `peeked` flag.
  - **As built (ticket 30):** the `?` (a `.reference-hint` at the left of the bar under the editor) shows the current Language's Reference Solution, from the Puzzle's per-Language table (`Common.Puzzle.languageTable`), in a tooltip that opens upward over the editor and stays open while the mouse is over it (so it can be read and selected). It reacts to the mouse only (no keyboard or touch path; the plan says hover). The page sends the Run two events, `HintOpened` and `HintClosed` with their times; the Run (`Common.Run`) decides, so the 1 s rule is pure and tested: it is peeked once the hint has been open for 1 s or more (a tooltip still open when the Run passes counts up to the moment of the pass). A peek counts from the page load, before the first keystroke, and during a Pause; it does not count after a skip or a pass. A new Run starts unpeeked. The mark reads "12.3 s (peeked)" in the end-of-Run result and beside a best that was peeked ("Best: 12.3 s (peeked).", "New best (was 14.0 s, peeked)."); there is no list of bests in the app yet, and the live clock does not carry it.

**Settled in the build (owner, 2026-11-11, code review of the branch).** Failed-test text is Language-neutral. A failed test is shown as its input, the expected value and what the Solution returned, in the form Puzzle prompts use for examples, whichever Language is shown and JavaScript included: `10 → "Buzz", got "3"`, several arguments separated by commas (`[1,2,3], 2 → [[1,2],[3]], got ...`), values as JSON. It was the call in JavaScript syntax (`fizzBuzz(10) should return "Buzz", got "3"`); `Common.Puzzle.callText` is now `inputText`, and puzzle-check's messages follow (`test 2 failed: -3 → expected 6, got -6`). Nothing else about the Run changes.

**Settled in the build (owner, 2026-11-10, from ticket 30).** A peek counts before the first keystroke and while Paused, not after a skip or a pass. The `?` tooltip is mouse-only (no keyboard or touch way to peek). A Run typed in several Languages counts in the "last 20" window of every Language it had key presses in; the record carries `keyLanguages` (Language and press count per stretch) only when the Run switched. The "peeked" word is shown as `12.3 s (peeked)`.

**Checks and errors** ([ticket 12](issues/12-grilling-check-latency-and-syntax-errors.md))
- Check 400 ms after the last edit, for every Language. A newer edit makes the older result ignored.
- The status line shows the first error only, as one cleaned line with line and column ("doesn't parse yet" for syntax errors, "doesn't type-check yet" for type errors). Hovering it shows all errors in full.
- Optional underlines for both Languages, a checkbox "Show error underlines" in the menu (after the two buttons, reachable by Tab, flipped with Space), on by default. They appear when a check finishes and disappear on the next edit. The status-line message stays either way.
- While a Language's compiler downloads: the status line reads "Loading <Language> compiler…" (with a percentage if available), the player can keep typing, and the first check runs when loading finishes. A failed download says so with a retry; switching to JavaScript always works.
  - **As built (ticket 31):** the Checker's result has `kind: "syntax"` (doesn't parse) or `"type"` (doesn't type-check) for a compile error, with the first error's `message` (one cleaned line, without its position), `line` and `column` (both count from 1, for both Languages: JavaScript's acorn column was 0-based until this ticket), `range` (at least one character), `ranges` (every error's range) and `all` (every error in full, as text). `Common.Run.CompileError` carries them. The status line reads `doesn't type-check yet: line 3, column 12: Could not match type String with type Int …` (or `doesn't parse yet: …`); the line is cut with an ellipsis when it is long, and its `title` (the hover) holds `all`. JavaScript's message is acorn's without its `(1:8)` suffix. The feedback line under the status no longer repeats a compile error. Underlines: `static/editor/src/underlines.mjs` (a CodeMirror state field: the ranges a finished check reported, cleared by the next edit and by a Language switch, drawn as a wavy underline in the `--bad` colour; the option turns the drawing off without losing them, so turning it on again shows the same ranges); the page sends them when a check of the draft shown finishes. The option is the checkbox "Show error underlines" at the end of the menu (a native checkbox in a label after the two buttons: Tab reaches it, Space flips it), kept first in `localStorage["type-solution.options"]` with unknown fields preserved (`storage.mjs`: `loadOptions`, `saveOption`). Loading: the trigger's start function reports to `static/editor/src/loading.mjs`; the Haskell page watches it (`TypeSolution.watchLoading`) and shows `Loading PureScript compiler… 42%` (the compiler's share of the download; no percentage when there is none) in place of the status line while the Language shown is loading and the Run is not Paused, Skipped or Passed, and `Could not load the PureScript compiler.` with a **Retry** button (`TypeSolution.retryLoading`) when it failed. A check made meanwhile waits for the download (a failed one keeps waiting for a retry) and runs when it finishes; the next pick of the Language also starts the download again.

**Saved data** ([ticket 16](issues/16-grilling-saved-data-and-options.md))
- Runs stay in the single list `localStorage["type-solution.runs"]`. Each new record has a `language` field; a missing one reads as JavaScript; old records are never rewritten. The storage-full rule (strip key presses from the oldest records first, never drop summaries) is unchanged and covers all Languages.
- Personal best, Most missed and Slowest are derived from the runs each time and never stored, filtered by the current Language. The "last 20 passed records" window counts only that Language's records.
  - **As built (ticket 30):** a record now holds `language` (the Language that passed; missing reads as JavaScript, `Common.Run.legacyLanguage`, the only place the Run or the history names a Language), `peeked` (boolean; missing is false) and, only for a Run typed in more than one Language, `keyLanguages`: consecutive stretches `[[language, count], ...]` saying which Language each of the `keys`/`gaps` was typed in (absent means every press was typed in `language`; stretches that do not add up to the presses are ignored). Words per minute and Backspaces are the passing Solution's; the time is the whole Run's. The storage-full rule strips `keys`, `gaps` and `keyLanguages` together and never touches `language` or `peeked`. A key press counts toward the Language it was typed in, so a Run is in a Language's window of 20 when it has presses typed in that Language (for a Run that never switched, exactly "that Language's records"); a Backspace run and a Hesitation never span a switch, and the first press of each stretch typed in a Language is not a Hesitation. Whichever Solution passes first ends the Run (L3): a check begins 400 ms after the last edit of its own Language (each Language waits out its own pause), whichever Language is then shown, and a check under way for the Language left still counts when it passes; its failure is not shown for the draft in front of the player.
- Own key `type-solution.language` (read once on page load). Own key `type-solution.options`: a JSON object, first field `underlines` (default on); missing key or field takes the default; unknown fields are preserved on save.
  - **As built (ticket 31):** `storage.mjs` `loadOptions` (the default for a missing key, bad JSON, a non-object, or a field that is not a boolean) and `saveOption` (writes `underlines` first, keeps every other field, never throws).

## The four seams

What a Language must supply ([ticket 19](issues/19-grilling-keeping-the-second-language-cheap.md)). Everything not listed here is shared app behaviour.

1. **Checker.** Typed code plus a Puzzle's tests in; pass, fail or a readable error (message, line, column, range) out. It includes the **calling convention**: how a test's JSON `args` and `expected` become a call and a comparison. That rule is per Language and documented in its folder. Per-Language settings: compile timeout and length limits (below). Global: the 400 ms pause.
2. **Editor mode.** Syntax colouring and indent rules; switching Language swaps only the editor's language extension.
3. **Import rules** (optional). How the Language adds an import line. A Language with none shows no popup and loses nothing else. The "one-line imports only" bank rule applies only to a Language that has imports.
4. **Bank folder** `languages/<name>/` (see Bank).

**JavaScript is the first Language, in the same terms.** The build refactors it behind these seams while adding PureScript, so there is never a second code path. Its check keeps the current behaviour: acorn parse, then a fresh worker per check, a ~1 s timeout, a spare worker.
  - **As built (ticket 31):** the fresh worker, spare, timeout and stopping are `static/editor/src/sandbox.mjs`, used by JavaScript's Checker and by PureScript's (each with its own runner script, `static/src/js/runner.js` and `purs-sandbox.js`): one mechanism, two scripts.

## Puzzle file

([ticket 04](issues/04-grilling-puzzle-file-per-language.md))

- `function`, `prompt` and `[[tests]]` stay at the top level, shared. Each Language has a table, `[javascript]`, `[purescript]`, holding `signature` and `reference`. A missing table is an error: every Puzzle has a Solution in every Language (L4), and puzzle-check fails a file without one. Existing files migrate by wrapping `signature` and `reference` in `[javascript]`.
- `Puzzle.hs` accepts the known Language tables and rejects unknown names.
- **Prompt:** one, Language-neutral. Examples are plain input → output pairs (`"internationalization" → "i18n"`); puzzle-check lints out Language-specific call syntax.
- **Limits, all Languages:** Reference Solution 4 to 30 non-blank lines and 100 to 900 characters, imports excluded. Existing JavaScript Puzzles need no change. (Per-Language limits are allowed in each Language's config; these are the defaults.)
- **PureScript signature:** two lines, shown above the editor and typed by the player (they count toward the limits):

      chunk :: forall a. Array a -> Int -> Array (Array a)
      chunk items size = ...

  - **Checked (code review, 2026-11-11):** puzzle-check fails a `[purescript]` signature that is not exactly these two lines (the first `<function> :: <type>`, the second `<function> <parameter names> = ...`), whose parameter count differs from the number of arguments of any test, or whose Reference Solution does not define the function with that many parameters (a point-free Reference Solution fails). All 50 Puzzles already have this shape, so no exception exists.

  Parameter names match the order the tests pass.

## PureScript

### Checker: a browser build of `purs`

([research 01](research/01-purescript-in-browser.md), [07](research/07-purs-browser-port.md), tickets [06](issues/06-grilling-checking-without-browser-compiler.md), [09](issues/09-grilling-port-go-no-go.md), [10](issues/10-task-build-purs-wasm.md), [11](issues/11-task-purs-wasm-in-browser-worker.md), [13](issues/13-grilling-compiler-bundle-build-and-deploy.md), [14](issues/14-task-build-native-wasm-ghc.md))

No maintained browser build of the PureScript compiler exists; the plan of record is our own port to WebAssembly, with no numeric gate (build, measure, then set limits). It has been built and run:
- Patched upstream `purescript` v0.15.16 on GHC 9.14's wasm backend; **2.3 MB brotli**, Prelude externs about 47 KB brotli.
- Browser (Chrome) worker run: unchanged check about 0.2 s, edited `Main` 0.3 to 0.4 s, cold Prelude build 3.4 s, about 20 MB memory. Type and syntax errors come back as readable text; the generated JavaScript runs after blob-URL linking. Needs a file modified-time that moves with edits.
- **Measured in ticket 28** (Chrome 157 and Firefox 158.0.1 on the owner's Apple-silicon Mac, a local static server, machine load average 25 to 40 so every time is pessimistic; harness `tools/purs-bundle/browser/`):
  - **`arrays`:** its pack is 69,804 bytes gzip (501 KB raw: sources, externs, compiled JavaScript); the Prelude pack 115,108 bytes gzip (1.0 MB raw). But `arrays` requires 28 other libraries, so a Solution with `import Data.Array` loads 29 libraries: 566,705 bytes gzip, a 6.1 MB file tree, 148 modules. The compiler still parses every source file it is given on each check, so a check of `import Data.Array` costs more than Prelude only. Chrome, first / unchanged / edited check: Prelude only 328 / 232 / 176 ms; `import Data.Array` 1119 / 598 / 556 ms with only the 91 reachable modules given to the compiler (Firefox: 141 / 120 / 120 and 470 / 365 / 377 ms). Giving the compiler all 148 cut the speed by about 40% (Node, same load: 2.7 s against 1.6 s). Memory 32 to 43 MB. The 400 ms check target therefore holds for Prelude-only Solutions but not for `import Data.Array` in Chrome on this machine; re-measure on a quiet machine before setting limits (ticket 31).
  - **Measured in ticket 31** (the real Checker in the exported app, `static/editor/browser/measure-purescript.mjs`: each check timed from `start` to the reply on the page, so it includes the worker's round trip, the sandbox and the linking; median of 8 `unchanged` and 8 `edited` checks after the first; Chrome 157.0.8103.50 and Firefox 158.0.1 headless on the owner's Apple M1 Max with 10 cores, local static server; **load average 5.4 to 7.4 on Chrome and 4.7 to 5.4 on Firefox, so not a quiet machine, but far less than ticket 28's 25 to 40**; the shim's debug logging, which the ticket 28 harness left on, is off):
    - Chrome, first / unchanged / edited, compiler's own time for an edited check in brackets: Prelude only 584 / 149 / 143 ms (141); `import Data.Array` 621 / 467 / 465 ms (428; 91 source files given); `chunk` (the Puzzle: `Data.Array`) 609 / 479 / 471 (433); `queryString` (typed path, 101 files) 684 / 540 / 541 (532); `withDefaults` (`Union`, `Nub`) 291 / 175 / 174 (166).
    - Firefox: Prelude only 539 / 110 / 108 (106); `import Data.Array` 660 / 325 / 328 (309); `queryString` 671 / 390 / 382 (377).
    - **The 400 ms target:** holds for Prelude-only in both browsers and for `import Data.Array` in Firefox (328 ms); **in Chrome `import Data.Array` is 465 ms, 16% over**, on a machine that was not quiet. No limit is decided.
    - **The typed path alone** (the same body and imports, `Eq a =>` against `Show a =>`): Chrome 470 against 483 ms edited (482 against 505 unchanged), Firefox 335 against 344: about 13 ms (3%) more, the one extra file in the compiler run.
    - The first check on a fresh page (compiler already in Cache Storage, worker started, libraries fetched and decoded, tree built) costs 0.3 to 0.4 s more than a later one, Prelude-only 584 against 143 ms; ticket 38 closed it: see "Warm-up (ticket 38)" under "Check behaviour".
  - **Bundle size:** compiler 23,585,103 bytes raw, 3.45 MB gzip -9 (3.53 MB at gzip -6), 2.27 MB brotli (ticket 27); all 40 packs 798,953 bytes gzip (7.4 MB raw); name table 61,517 bytes. The first PureScript pick fetches only the pointer, manifest, compiler and name table (Chrome, local server: 152 to 515 ms to ready, compiler `WebAssembly.compile` 28 to 98 ms in the worker).
  - **Real network (proxy):** the bundle is not deployed, so GitHub Pages itself was measured with the app's own `ghcjs/frontend.wasm` (6.7 MB raw, served as 1,671,299 bytes gzip): 1.37 s on a cold edge (1.2 MB/s), 0.12 to 0.14 s warm (12 MB/s). That puts the compiler's 3.5 MB gzip at roughly 0.3 s warm to 3 s cold on this connection. This is an estimate, not a measurement of the bundle. Pages answers `Accept-Encoding: br, gzip` with **gzip** (no brotli) for HTML, JavaScript and `application/wasm`, with `cache-control: max-age=600` and an ETag; the 2.3 MB brotli figure is therefore not what players download, 3.5 MB is. No contradiction with the plan: the plan says "brotli" as a size figure only.
  - **Not measured, and why:** Safari (needs `safaridriver --enable`, an administrator step, and a Develop-menu setting; not possible in a non-interactive session); low-end or mobile devices (none to hand); the bundle on real GitHub Pages (not deployed until the app is wired to it, ticket 31/33); the real deployed Solution sandbox; the order of Cache Storage quota limits per browser. Second-visit behaviour is shown in Chrome (a reload with PureScript remembered asks only for the pointer, plus, since ticket 38, the library packs of the Puzzle that opened if they are not in Cache Storage yet); Firefox made two pointer requests there, not investigated.

**Build and shipping**
- **`purs-core.wasm` is built in its own repository, [jafonsor/purs-wasm](https://github.com/jafonsor/purs-wasm), and shipped as a GitHub Release asset** (amended 2026-11-06, replacing "a Nix package in the app's own `nix build`"). That repo holds the Nix recipe and a GitHub Actions workflow that builds the `gmp`-free GHC and `purs-core.wasm` (cold GHC about 1 h on a runner, then cached), pruned-GHC and Node smoke checks, and a release on a version tag. This repo fetches the released file with `fetchurl` and a pinned hash, so the app's `nix build` and `deploy.yml` never compile GHC. Externs and compiled library JavaScript (ticket 28) are built here from the pinned list, with the released wasm as input. The released wasm is the source of truth: a GHC rebuild does not reproduce its bytes.
- **Patches:** a patch file in this repo applied to pinned upstream (no fork). It lives in `jafonsor/purs-wasm` (`nix/purescript/purescript.patch`, entry point `purs-core-Main.hs`).
- **Toolchain:** a `gmp`-free wasm GHC 9.14 (flavour `perf+native_bignum`, no `--with-intree-gmp`), built from the `haskell-wasm/ghc` `ghc-9.14` branch, instead of the repo's prebuilt `gmp` one. This was proven in [ticket 14](issues/14-task-build-native-wasm-ghc.md): 34 min to build on a 10-core Mac, `purs-core` unchanged, byte-identical compiler output (not the wasm itself: rebuilds with a different GHC give different wasm bytes, see ticket 27), 2.28 MB brotli, same speed, no `gmp` in the binary. Recipe and scripts: `research/10-purs-wasm/` (`ghc-native-build.sh`, `ghc-native-install.md`, `ghc-native-install.sh`, `purs-core-build-with-native-ghc.sh`). No `gmp` licence note is needed for the compiler bundle (this reverses [ticket 13](issues/13-grilling-compiler-bundle-build-and-deploy.md)'s toolchain choice, per the owner). **Not yet done:** running the `native`-built compiler in a browser. Packaging it in Nix and building it on Linux CI is done in [jafonsor/purs-wasm](https://github.com/jafonsor/purs-wasm): a cold GHC build took about 1 h on a GitHub runner (about 2 h 54 min under Docker with Rosetta), and the pruned install is about 84 MB as `tar.xz` ([research 12](research/12-ghc-wasm-compression.md)). Running the `native`-built compiler in a browser is still ticket 33's job. The app's own `frontend.wasm` still links `gmp`; that is unchanged by this spec (a `native` frontend build was shown to work only on the Obelisk-free prototype).
- **Libraries:** a committed list, `languages/purescript/packages.json`, is the source of truth, naming one pinned package-set release and, per library, its version, repository, commit and module names. The library sources are not committed; the Nix package fetches them and builds externs and compiled library JavaScript for exactly that list. puzzle-check fails if a Reference Solution imports a module outside the list, reading only the committed file; to compile, and to check imported names, it needs the sources in a folder named by `PURS_LIBS` (only where they are, never which).
- **Serving:** the bundle is separate from the main one, with a content hash in every file name except the one pointer, `current.json` (owner accepted this exception, 2026-11-10; GitHub Pages sets no cache headers), kept in Cache Storage; old versions deleted when a new one is stored. A hashed manifest maps each library to its externs; a library's externs are fetched only when a Solution imports it. No CSP change (the page has none).
  - **As built (ticket 28; `tools/purs-bundle/`, `static/bundle/`, flake output `purs-bundle`):** the build writes, per library, one **pack** `<library>.<hash>.pack.gz` holding its sources, its modules' `externs.cbor` and compiled `index.js`/`foreign.js` (so "a library's externs" are fetched together with its JavaScript, in one request); a manifest `manifest.<hash>.json` (per library: file, sizes, `requires` = all libraries it needs, `modules`; module to library; compiler; `sourceMtime`); the compiler `purs-core.<hash>.wasm`; and the name table `names.<hash>.json` (module to exported names, with the clash preferences, for the import popup). The hash is the first 16 hex digits of the sha256 of the content (of the uncompressed pack for a pack, so a different zlib version does not rename it). Packs are gzip-compressed by us, so the size does not depend on what Pages compresses. Two builds of the same inputs give the same bytes with one Node version; across Node versions (Nix's and a developer's) the packs' gzip bytes differ, and with them the sizes the manifest records and so its own name, but the packs' names and decoded content do not (checked: the Nix build and a local Node 24 build have all 40 pack names identical). The Nix build is the one to deploy.
  - **One fixed name, the pointer** `current.json` (`{"manifest": "manifest.<hash>.json"}`), fetched with `cache: "no-cache"` (revalidates by ETag despite `max-age=600`). This is the one exception to "a content hash in every file name"; without it the page cannot learn the manifest's name without changing the app's own build.
  - **Cache Storage:** one cache, `purs-bundle`, holding the files of one manifest. Opening a manifest the cache does not hold deletes every cached file it does not name (a file whose hash did not change, such as the compiler, stays). Offline, the stored manifest is used.
  - **Compiler worker rules the data imposes (ticket 31):** build the tree with `assembleTree` and `librariesFor` (`static/bundle/purs-tree.mjs`); every file from a pack must report the manifest's `sourceMtime` as its modified time (sources, externs and JavaScript alike) and `Main.purs` a later one that moves with edits, else the compiler rebuilds the libraries (3 s for Prelude, 79 s for the `arrays` closure in Node); pass the compiler only the sources reachable from the Solution's imports (`sourcesFor`).
- **Download timing:** on the first PureScript pick, or at page load if PureScript is the remembered Language. JavaScript-only players pay nothing.
- **Reference Solution check:** puzzle-check compiles every PureScript Reference Solution with this compiler and fails on any error. This also guards against the 9.14 version drift. The check runs the same `purs-core.wasm` the browser downloads, in Node through WASI, as a runner behind `npm run solutions` ([ticket 21](issues/21-task-puzzle-check-runs-purs-wasm-in-node.md)); not a native `purs`, and not a browser.

**Check behaviour**
- One long-lived compiler worker, kept between checks; each check gets a fresh compiler instance in it with a persistent in-memory file tree. Compile timeout about 5 s (a safety net); only on timeout is the worker killed, and the new one rebuilds its tree from the saved downloads. The ~1 s timeout applies only to running the generated JavaScript against the tests, in a fresh sandbox as today. No spare worker.
- Library results are shipped, not persisted per check. No OPFS (an option if the first check feels slow). A warm-up runs after load and when a new Puzzle opens (and when the Language shown changes), for the Language shown only; a real check goes first. **As built (ticket 38):** see "Warm-up" under the Checker's As built note.
- PureScript syntax errors report the line after the break, so an underline goes at the end of the last non-blank line before the reported position.
- **As built (ticket 31;** `static/editor/src/languages/purescript/`**; scripts built by esbuild next to `runner.js` as `js/purs-compiler.js` and `js/purs-sandbox.js`, found beside the runner script's address by plain name).** `loader.mjs` owns the download (`bundle.start`, progress, retry; `ready()` for the Checker; `names()` for the import popup) and compiles the compiler on the page; `check.mjs` is the Checker; `compiler.mjs` and `compiler-worker.js` are the worker (a `WASI` shim, `@bjorn3/browser_wasi_shim` 0.4.2, over an in-memory tree; pass `{debug: false}`: the shim logs every system call to the console when `debug` is absent, which the ticket 28 harness did not know); `errors.mjs` turns the compiler's text into the Checker's error; `calling.mjs` and `sandbox.js` are the calling convention.
  - **The worker** is made at the first compile (no spare), is sent the compiled module and `sourceMtime`, then each check's source, the Harness (or none), the imported modules and the libraries' decoded packs it does not hold yet (the page keeps the packs, so a new worker is given them again). The tree is rebuilt only when the set of libraries grows (so Main's externs are kept for an unchanged set). Each check makes a fresh `WebAssembly.Instance`, gives the compiler `sourcesFor(packs, imports)` (91 of 148 modules for `import Data.Array`; the Harness adds `Prelude` to the imports) and returns, on a clean compile, the generated JavaScript of Main (or Harness) and everything it reaches. Compile timeout 5 s from when its compile starts; only then is the worker killed. A newer check waits for the compile in flight (the worker cannot be interrupted) and the older result is dropped; a check made stale while it waits never compiles.
  - **The sandbox** (`sandbox.js`) gets `{modules, main, fn, tests, dicts, typed}`, links the modules through blob URLs, and calls as before: one argument per constraint kind (`eq` supplies `{eq: a => b => a === b}`, `other` supplies `{}`), `t<i>()` on the typed path, Tuples as pairs, the JavaScript runner's pass rule. The 1 s timeout starts when the request is sent, so linking counts; the sandbox is a fresh worker each time.
  - **Errors** (`errors.mjs`, texts as `purs` 0.15.16 prints them): warnings (unused names, redundant imports) precede errors and are not errors; the first error's message is the body up to the `See https://` link, blank lines dropped, one line, 300 characters (the same cleaning as puzzle-check's `firstError`); `all` keeps each error's lines as printed (with the colour padding lines removed) under `line L, column C`, numbered when there are several. An error whose file is `Harness.purs` is `crash`: `the generated test module does not compile: line:col message`; a typed path with a value that has no PureScript type is `crash`: `cannot call f from the tests: test 2 args[0]: …`. **Syntax errors** (`Unable to parse module`): if the reported position has only white space before it on its line (the compiler reports the line after the break), the underline is the last character before the position that is not white space, i.e. the end of the last non-blank line; a position in the middle of a line is the token itself. Positions are the player's own (the `module Main where` header the Checker adds when the Solution has none is taken off). Type error ranges are the compiler's span, at least one character, cut to the text.
  - **Warm-up (ticket 38).** An optional seam: a Language says `canWarmUp: true` and its Checker has `warmUp(code, fn, tests)` (the Puzzle's Reference Solution in a check's request form); JavaScript has neither and does nothing. The page (`Frontend/Run.hs`, Language-agnostic) asks `TypeSolution.canWarmUp(language)` and, if so, hands the Language's Checker the Reference Solution once at load, for each new Puzzle (both menu buttons) and when the Language shown changes; the text stays inside the Checker (not in the editor, the tooltip, drafts, key presses or the Run record; no Run event, so the clock and Run state are untouched). PureScript's has two parts, both silent on failure:
    - **Preload (worker real checks use).** Once the compiler has loaded (`loader.whenLoaded()`, which never starts the download), it fetches the libraries the Reference Solution imports, starts the compiler worker and sends it the decoded packs (`{type: "preload"}`): the tree is built, nothing is compiled, nothing is in flight. The worker answers `preloaded`; only then does the page count those libraries as held, so a real check that meets a preload half done sends the libraries again (the worker ignores a pack it holds) and never relies on it. The tree build is 1 to 7 ms in Node (decoding 25 to 28 ms), so what preload saves is mostly the fetch and decode, which on a real connection is the larger part.
    - **Throwaway compile (separate worker).** Preload alone left Chrome's first check 143 to 189 ms over a later one (Prelude only 304 against 161; Firefox was already within 15 to 66 ms): the first compile of a page costs about 0.15 s more than a later one whichever worker made it: an engine warm-up). So the Reference Solution is also compiled once in a second, disposable compiler worker with its own copy of the libraries, and the result is dropped. A worker cannot be interrupted, only terminated, so that one is terminated the moment a real check starts, an edit stops the Checker, the compile ends, or 5 s pass; the worker real checks use is never given a compile, so a real check never waits behind one. Neither part starts while a check is in flight or a compile is under way, and a real check cancels a warm-up still fetching. Cost: a second worker and a second copy of the libraries (up to about 6 MB for `import Data.Array`, 32 to 43 MB while compiling) for at most one compile, once per Puzzle.
  - **Measured (ticket 38)** with `static/editor/browser/measure-purescript.mjs` (`WARM=ready|preload|during`: each check timed from `start` to the reply, the first on a fresh page, the compiler downloaded and ready first; "later" is the median of 8 edited checks of the same Solution; Chrome 157.0.8103.50 and Firefox 158.0.1 headless, Apple M1 Max, 10 cores, local static server; **machine load average (1 minute) in brackets**, never a quiet machine):
    - Chrome, first / later (ms): no warm-up (compiler ready) Prelude only 283 / 141 (5.3), `import Data.Array` 631 / 458 (5.1), `chunk` 665 / 473 (4.8), `queryString` 597 / 538 (5.9); **with the warm-up 162 / 144 (5.6), 500 / 460 (6.0), 502 / 466 (5.3), 558 / 526 (5.2)**: 18, 40, 36 and 32 ms over a later check, all within 50.
    - Firefox: no warm-up 135 / 108 (6.4), 415 / 335 (6.5), 407 / 334 (6.1), 477 / 389 (6.2); **with the warm-up 117 / 107 (6.6), 352 / 326 (6.3), 361 / 344 (6.4), 404 / 395 (6.2)**: 10, 26, 17 and 9 ms over.
    - Preload only, before the throwaway compile existed (Chrome, load 8 to 12): Prelude only 304 against 161 later, `import Data.Array` 694 against 519, `chunk` 708 against 519: 143, 175 and 189 ms over, which is why the throwaway compile is there. A throwaway compile in a second Checker's worker before the first check (an experiment, same load) gave 186 / 156, 570 / 509 and 622 / 554 in Chrome and 122 / 115, 374 / 345 and 371 / 347 in Firefox, so it is the engine, not the first worker, that is cold.
    - **A real check started while the warm-up runs is never slower** (first check of a fresh page, `chunk`, started 150 ms into the warm-up, so the throwaway worker is killed mid-compile; sorted figures, ms): Chrome (load 10 to 14) without a warm-up 698 705 707 714 718 718 721 722 730 731 734 737 738 740 742 873, with 590 590 592 596 604 605 608 615 616 629 631 634 636 687 713 737; Firefox (load 13 to 14) without 430 433 434 437 441 444 445 447 454 472 495 506, with 374 378 378 379 380 381 386 389 398 419 460 605. Medians: 731 against 616 in Chrome, 445 against 381 in Firefox; one Firefox sample in twelve (605) was slower than any without, on a machine at load 14, and none of the 16 Chrome ones. A partly done warm-up still helps, because the engine is warmer. Not proven for a machine with one or two cores, where a worker killed a few milliseconds after it began competing for the CPU is the one place a delay could hide.
### Calling convention

([research 02](research/02-purescript-json-tests.md), ticket 04)

Calls are curried. Of 185 tests in 50 Puzzles, 31 Puzzles map to plain PureScript types; the rest:
- **Polymorphic lists** (`chunk`, `everyOther`, `positions`, `rotate`, `unique`, `grid`, `flatten`, `zip`): `forall a.`; `flatten` is one level; `unique` and `positions` need `Eq a =>`; `zip` returns `Array (Tuple a b)`, converted to JSON pairs by the harness.
- **One-value-type objects** (`countWords`, `groupByLength`, `invert`, `mergeCounts`, `toggleFlags`, `topScorer`, `totalCost`) and `pick` (`forall a. Object a -> Array String -> Object a`, which also takes mixed values): `Object a`.
- **Mixed-value objects:** `queryString` keeps an advanced type, `forall r rl. RowToList r rl => Keys rl => Record r -> String`, with a `Keys` class the Solution writes and walks over the row (the harness builds its dictionary, see below); `withDefaults` too: `forall a b c d. Union a b c => Nub c d => Record a -> Record b -> Record d`, solved by `Record.merge` (`Record` library; `Union` and `Nub` from `Prim.Row`). Tests untouched.
- **`getPath`**: `Json -> String -> Json` (`Data.Argonaut.Core`, `argonaut-core`), a deliberate interop Puzzle. Tests untouched.
- So every Puzzle gets a PureScript Solution; L4 holds with no exceptions.
- **Settled by compiling** (ticket 23, `purs` 0.15.16, package set `psc-0.15.16-20261104`; all 12 hard Puzzles pass `npm run solutions -- --lang=purescript`):
  - `Type.Proxy` is the right module name; it lives in the `prelude` library (v6.0.3), not a separate package. `RowToList`, `Cons` and `Nil` come from `Prim.RowList`, `Union` and `Nub` from `Prim.Row`; the pinned-library lint lets `Prim.*` through.
  - **Dictionary passing is as guessed, and wider.** Every constraint in a function's type is one extra leading argument: `unique(dictEq)(items)`, `positions(dictEq)(items)(value)`. Row-solved constraints (`Union`, `Nub`, `RowToList`) take an argument too, and ignore it: `withDefaults()()(options)(defaults)` in the compiled JavaScript. The tests carry only JSON, so the harness reads the constraints off the function's signature in the Solution text (`dictionaryKinds` in `tools/puzzle-check/purs-runner.js`) and supplies one argument per constraint, in order: for `Eq` the dictionary `{eq: a => b => a === b}` (what `Data.Eq` builds for `Int`, `String` and `Boolean`; it does not compare nested arrays structurally), for any other class `{}`. The browser harness must do the same. A dictionary with real methods (`Ord`, `Show`, a user-written class) cannot be supplied by hand; the typed path below has the compiler build it.
  - **`Tuple` is as guessed.** `Data.Tuple.Tuple` compiles to a JavaScript class named `Tuple` with `value0` and `value1`; the worker's `constructor.name === "Tuple"` check works (`zip` passes). A bundler that renames classes would break it (the browser worker should keep names or check `value0`/`value1` shape on instances of the `Data.Tuple` module's `Tuple`).
  - **`queryString` keeps the RowToList-and-class type** (ticket 35). A user-written class's dictionary holds methods that depend on each test's record shape, which JSON cannot give the harness, so the harness has the compiler build it: **the typed path**. When a function's signature has any constraint other than `Eq` or a row-solved one (`Union`, `Nub`, `Lacks`, `Cons`, `Append`), the runner writes a module `Harness` next to the Solution, one function per test, `t0 _ = queryString { "page": 2, "q": "cats" }`, with the arguments as PureScript literals typed from the test's JSON, and compiles both in the same compiler run; the compiler picks the instances, and the worker calls `t<i>()` and compares as before. Tests stay JSON and Language-neutral (L2). JSON to PureScript: string -> `String`; integer within 32 bits -> `Int`; any other number -> `Number`; boolean -> `Boolean`; object -> record with quoted labels, nested objects nested records; array -> `Array` of one element type. Anything else fails with a readable message naming the test and the place (`test 2 args[0].a[0]: null has no PureScript type`): `null`, an array of mixed types, an empty array (no element type), a string with a character outside printable ASCII, a number written with an exponent. A test whose values the Solution has no instance for (for example a `Boolean` field where only `String` and `Int` have a `Field` instance) fails as "the generated test module does not compile: line:col message". The Solution's own compile errors are reported as before. This also lets `Ord` and `Show` constraints through, since the compiler resolves them at the test's concrete types. **What it still cannot do:** call a function that takes `Json`, `Object a`, `Maybe`, `Either`, `Tuple` or a function as an argument and also has a typed constraint (the literals are plain records, arrays and scalars); and anything where the test's values do not fix the types (empty arrays). **Cost, measured** (ticket 35, Node, `purs` 0.15.16, a busy machine with load average 10, median of 8 warm checks): `queryString` 1.19 s against 1.23 s for `chunk` and 1.20 s for `withDefaults`: no measurable difference, because the `Harness` module is one small extra file in the same compiler run (no second compile and no second process); the dominant cost is the compiler loading the libraries' externs, same for every Puzzle. The first check of a process pays that load once (25 s on the same loaded machine; about 3.5 s unloaded per ticket 21). The cheap path (Eq dictionary, `{}`) is unchanged for the other 11 Puzzles. **As built and measured in the browser (ticket 31):** the Checker applies the same rule (`calling.mjs`, kept equal by `tools/puzzle-check/test/browser-twin.test.js`); see "Measured in ticket 31" under Checker for the typed path's cost.
  - Libraries used: `prelude`, `arrays`, `maybe`, `tuples`, `strings`, `foreign-object`, `argonaut-core`, `record` and their dependencies (list in ticket 23's Comments).

### Import rules and the import popup

([ticket 08](issues/08-prototype-auto-import.md), prototype in `prototype-auto-import/`; [ticket 17](issues/17-task-auto-import-in-codemirror.md), prototype in `prototype-auto-import-codemirror/`)

- **Popup:** after 2 letters, on names in a name-to-module table, up to 6 matches, each shown with its module. Never on an `import` line. It stays open while typing. Esc closes it; clicking elsewhere closes it. Names already imported and Prelude names are not offered.
- **Accepting:** Tab or Enter adds **only the import line**; the typed letters are untouched and the player still types the whole name. Up/down move the highlight. While the popup is open Enter accepts instead of making a newline. With no popup, Tab still indents (two spaces). Dropping Enter-accepts is a one-line change if it annoys.
- **Import edit:** if `import M (...)` exists, merge the name into it (`take` then `drop` gives `import Data.Array (take, drop)`); otherwise add a line after the last import, or at the top with a blank line below when there are none. The cursor keeps its place relative to the typed text.
- **Counting:** the import line is inserted text, not typed: not a key press in the Run record, not in words per minute, excluded from the line and character limits. Everything else the player types counts, names included.
- **CodeMirror build requirements** (verified in Chrome with `@codemirror/autocomplete` 6.20.4):
  - Completion `apply` is a function that dispatches only the import edit (one transaction, one undo step, cursor mapped automatically), tagged `userEvent: "input.complete"` so the key recorder can tell it from typing.
  - A highest-precedence Tab binding runs `acceptCompletion` and returns `false` when no popup is open, so `indentWithTab` handles Tab.
  - Set `activateOnTypingDelay: 0` and `interactionDelay: 0` (defaults made an early Tab indent instead of accepting).
  - Do not use `validFor` (it keeps showing an already-imported name).
  - Call `closeCompletion(view)` at the end of `apply`.
- **Tested in ticket 32** (`static/editor/browser/drive-imports.mjs`, 38 of 38 checks in Chrome 157 and 38 of 38 in Firefox 158.0.1, headless, on the exported `nix build` output with the shim rebuilt from the same sources plus a test registration of PureScript; the name table loaded from the built `purs-bundle` through `static/bundle/bundle.mjs`):
  - **Other browsers:** Firefox behaves as Chrome in every check (popup, Tab and Enter accept, merge, Esc, click-away, undo, Tab indent, Language switch). One difference: a Tab pressed 0 ms after the last letter accepts in Firefox but indents in Chrome (5 ms is flaky in Chrome, 10 ms or more accepts in both); no person types that fast, so it is recorded, not fixed.
  - **The app's key-press recorder:** tested for real. A Run typed with two accepted imports (Tab for one, Enter for the other, one of them a merge) has a record whose `keys` equal exactly what was typed; the accepting Tab and Enter and the import text are not in it. Without the guard (`acceptsPopup` in `editor.js`) the record holds the `\t` and the check fails. The import edit still reaches the Run as a code change, so the Solution that is checked and saved (`solution`) contains the import line.
  - **Not tested:** Safari (WebKit): `safaridriver --enable` is an administrator step and this session may not run it (the same limit ticket 28 hit; the permission system denied it again); touch keyboards (no device or software keyboard to hand; desktop browsers emulate neither a soft keyboard nor its Tab and Enter, and a phone has no Esc), and input methods that compose text (the key recorder ignores composing keys as before; the popup was not tried with one).
- **Imports are one line only** (see Bank), because the merge handles only `import M (a, b)`; `Type(..)` is an item of that list.
- **As built (ticket 32).** The popup is Language-agnostic: `static/editor/src/import-popup.mjs` builds it from a Language's `importRules` seam, `{names, isImportLine, offers, importEdit}` (documented in `languages.mjs`); a Language without `importRules` (JavaScript) gets no popup and Tab only indents. `editor-mode.mjs` puts the popup in the same Compartment as the mode, so a Language switch swaps both and nothing else. PureScript's side is `static/editor/src/languages/purescript.mjs` and the folder `languages/purescript/` (the only files in `src/` that name PureScript, besides the two lines of `languages.mjs` that list it; a test keeps it so). It exports the mode, the import rules and `purescriptEditorSeams({loadNames})`, which ticket 31 spread into the Language value (it is registered, so the dropdown lists PureScript); `namesFromBundle(bundle)` reads the `names` file of the bundle. The rules as built:
  - **Offered:** names an identifier can be typed as (values, types, classes; no operators) whose first letters match what was typed, ignoring case, in alphabetical order, up to 6. A name two or more modules export is listed once per module, the preferred modules first (`name-clashes.json`; only the preferred ones when the name has a preference, otherwise every module that exports it, alphabetical). Not offered: any name `Prelude` exports (from any module that re-exports it), any name the document already imports from any module (including `class` and listed constructors), the names of a module imported whole (`import M`), and anything on an `import` line.
  - **Edit:** one change. A class is imported as `class Name`. A merge goes before the closing `)` of the first `import M (...)` line of that module; a bare, `as`, `qualified` or `hiding` import is never merged into (a new line is added instead).
  - **Colouring and indent:** the Haskell mode with a wrapper (`forall`, `ado`, `derive` keywords, `true` and `false` literals, operators as operators, `"""` raw strings across lines). Enter keeps the last line's indent and adds one unit after a line ending in `where`, `do`, `ado`, `of`, `let`, `then`, `else`, `=`, `->`, `<-` or `\`.
  - **Keys:** Tab or Enter that accepts the open popup is not reported to the Run; Esc with the popup open closes only the popup (a second Esc opens the menu as before).
  - **Popup look:** it uses the editor's colour variables, so it follows the light and dark schemes.
- **As built (ticket 39): constructors.** Typing `Just` or `Nothing` offers it with its module (`Just  Data.Maybe`); accepting adds `Maybe(..)` (the type with all its constructors), never `Just` alone. The name table's rows are `[name, kind]` as before plus two: a type whose module exports all its constructors (`T(..)`) has kind `data`, and each of its constructors is `[name, "constructor", "T"]` (`["Just", "constructor", "Maybe"]`). `tools/puzzle-check/purs-exports.js` derives them from the pinned libraries (`exportsOf` reads the constructors from the `data`/`newtype` declaration, in the declaring module for a re-export; `nameRows` makes the rows; `tools/purs-bundle/build.mjs` writes them); nothing is hand-listed. A type exported with only some of its constructors would get no constructor rows (none in the pinned set).
  - **Offered:** the same rules as any name (2 letters, ignoring case, alphabetical, 6, preference list), the label being the name typed (`Just`, `Maybe`, `Left`) and the module on the right. A type with constructors is offered as the type (`Maybe  Data.Maybe`) and accepting it imports `Maybe(..)` too; a type without constructors (`Void`) is imported bare. A type and a constructor of one name in one module (`Tuple`) are one offer. Not offered: constructors of a type the document imports as `Type(..)` (`Just` and `Nothing` after `Maybe(..)`), a constructor already listed by name (`Maybe(Just)` hides `Just` only), and any name already imported (so a bare `Maybe` is not offered again, while `Just` still is).
  - **Edit:** still one change. `Type(..)` is merged like any name (`import Data.Maybe (fromMaybe)` becomes `import Data.Maybe (fromMaybe, Maybe(..))`; no import: a new `import Data.Maybe (Maybe(..))` line, placed as before). If a list of that module already has the type bare (`Maybe`) or with some constructors (`Maybe(Just)`), that entry is replaced by `Maybe(..)`, not a second entry (the first line of the module that has it, in any of its `import M (...)` lines).
  - **Clashes:** the preference list works on constructor names as on any name; `Pattern` (Data.String first) was already there, and `Nil`, `Cons`, `NonEmptyList` (an everyday module, `Data.List`, and the lazy list modules export different things) were added.
  - **puzzle-check:** an import `T(..)` must name a type the module exports with constructors, `T(A, B)` constructors it exports (`import Data.Maybe (Maybe(..))` passes; `Maybe(Foo)` and `Void(..)` fail). All 50 PureScript Reference Solutions still pass (15 import `Maybe(..)`, `Pattern(..)`, `Tuple(..)` or `Proxy(..)`; the check now reads their constructors, and `Type.Proxy`'s `data Proxy :: ...` kind signature before its declaration needed handling).
  - **Name table size:** 61,517 bytes (2,582 rows) before, 65,364 bytes (2,687 rows: 105 constructor rows, 86 `data` kinds) after, +3,847 bytes (+6.3%); 9,051 bytes gzipped. Measured on `names.<hash>.json` from `nix build .#purs-bundle`.
  - **Known limit:** after only `Not` the six places go to `Not` (two type-level classes in `Type.*`), `note` and `notElem`, so `Nothing` shows from `Noth` on. The order is the plain alphabetical one of ticket 32; changing it is the owner's call.

## Adding a second Language: the checklist

Do not pick it here. A Language is "cheap" if it needs only:
1. A Checker that runs in the browser in a worker, with no server.
2. A lazy-loadable bundle with a pinned build recipe.
3. An Editor mode.
4. Import rules, or an explicit "none".
5. A `languages/<name>/` folder.
6. A Reference Solution and signature for every Puzzle.
7. A calling-convention note.
8. puzzle-check compiling or running every Reference Solution.

## Where the build differs from the plan

Written 2026-11-11, after the build and its whole-branch review. Each item says where the detail lives; the owner's answer is recorded where there was one.

- **Compiler download size.** The plan quoted 2.3 MB brotli. GitHub Pages serves gzip even when brotli is offered, so players download about 3.5 MB (3.45 MB at gzip -9). Detail: "Bundle size" under Build and shipping. Owner: no change.
- **One file without a content hash.** The pointer `current.json` has a fixed name so the page can find the manifest without a change to the app's own build; it is fetched with `cache: "no-cache"`. The plan said every file. Owner accepted (2026-11-10).
- **A library's externs travel in its pack.** The plan said a manifest maps each library to its externs; the compiler also needs the sources, so the manifest maps a library to one pack holding sources, externs and compiled JavaScript (ticket 28).
- **Check time.** The 400 ms target holds for Prelude-only Solutions in both browsers and for `import Data.Array` in Firefox (328 ms). In Chrome `import Data.Array` takes 465 ms, 16% over, on a machine that was not quiet. No limit set; re-measure when the first real deploy exists (ticket 37).
- **Preloading (ticket 38).** The plan says an optional low-priority warm-up compile runs after load and when a new Puzzle opens, a real check first. Built as written in outcome, but not in mechanism: a compile cannot be interrupted in the worker real checks use, so the warm-up is a preload of the Reference Solution's libraries there (no compile) plus a throwaway compile in a second disposable worker that is terminated when a real check starts. The first real check after load is now 9 to 40 ms over a later one in Chrome and Firefox (it was 0.15 to 0.4 s). It adds one Language-agnostic optional seam (`canWarmUp`, `warmUp`) and a Haskell edit in `Frontend/Run.hs` and `Frontend/Js.hs` (L5: JavaScript has neither and does nothing). Detail: "Warm-up (ticket 38)" under the Checker's As built note. When a check can start during a warm-up on a one or two core machine is not measured.
- **Stale worker scripts after a deploy.** `purs-compiler.js` and `purs-sandbox.js` are found beside the hashed `runner.js` by plain name, and Pages caches those names for `max-age=600`. For up to 10 minutes after a deploy an old worker script can meet the new page. Making them hashed would mean naming PureScript in `Frontend.hs`, against L5. Owner accepted (2026-11-11).
- **Failed-test text is Language-neutral.** The failed-test message shows plain `input → expected, got actual` for every Language, JavaScript included, and puzzle-check's author messages follow the same form. The plan was silent; owner chose it and confirmed puzzle-check's wording (2026-11-11).
- **Adding a Language still touches `Puzzle.hs`.** `Puzzle` has one field per Language, the parser reads each Language's table by name, and `languageTable` matches on the names. This is the plan's own "`Puzzle.hs` accepts the known Language tables", but it is a Haskell edit that L5 would prefer not to need. A `Map Text LanguageTable` would remove it; not done (recorded in ticket 33's code review).
- **Browsers.** Tested in Chrome and Firefox only. Not tested: Safari, touch keyboards, composing input methods, low-end and mobile devices. Owner: enough for now (2026-11-11).
- **Release assets.** The release has five files (the wasm, the GHC tarball, their two `.sha256` files and `BUILDINFO.json`), not four. The pinned wasm hash is the one the Actions run printed (`95a037c8…`), not the Docker build's (`7e95c64d…`); a rebuild with a different GHC store path gives different wasm bytes.
- **Two workflows never ran in Actions.** `deploy.yml` (bundle steps, ticket 37) and `purescript-smoke.yml` (ticket 33) were validated locally and with `actionlint` only. Real Pages cache headers and the compiler's download time are still to be measured on the first real deploy.

## Out of scope

- Rewriting the app's own implementation in another language.
- Server-side compilation or checking.
- Accounts or sharing of Personal bests across browsers.
