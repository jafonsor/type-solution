# 10: Build purs as a browser WebAssembly module and measure it

## Question

Per [ticket 09](09-grilling-port-go-no-go.md): build a library-only `purs-core` for `wasm32-wasi` with the GHC 9.8 `native` flavour, following the plan in [research 07](../research/07-purs-browser-port.md) section 7, then run it in a web worker in the app page and check one small `Main` module against `Prelude` externs shipped as static files.

Record, as the answer: wasm size (raw, gzip, brotli), start-up, memory, one-module check time, externs size, what had to be patched, and what failed. Those figures feed the check-latency, syntax-error, build/deploy and fallback fog on the map.

This ticket does, rather than decides; the map's Destination is a spec, so confirm with the user before starting.

## Answer

**Plain version: it works.** The PureScript compiler built for WebAssembly and checked real PureScript. In Node (not yet a browser) it compiled all of Prelude plus a small `Main` in 3.4 s the first time, and re-checked just `Main` in 0.3 to 0.45 s afterwards, including a correct type-error report. The download is about 2.3 MB brotli. The 400 ms edit pause is in reach but not guaranteed, and the browser itself is still untested.

**Toolchain (deviates from [ticket 09](09-grilling-port-go-no-go.md)).** ghc-wasm-meta has no GHC 9.8 or `native` build for macOS arm64 (only 9.10, 9.12, 9.14, all `gmp`). Per the user, used the toolchain already in the Nix cache: GHC 9.14.1 wasm. So 9.8 and "no `gmp`" did not happen; the binary statically links `gmp` (LGPL) as the default flavour does. Behaviour drift from `purs`'s 9.8 pins is untested beyond the checks below.

**Figures** (`purs-core.wasm`, library `purescript` v0.15.16 from git tag, `-O1`, no `wasm-opt`/strip, not size-tuned):

| What | Figure |
|---|---|
| wasm size | 23.8 MB raw, 3.5 MB gzip -9, 2.3 MB brotli -q 11 |
| Prelude externs (v6.0.3, 50 modules) | 736 KB raw (53 `externs.cbor` files), 65 KB gzip, 47 KB brotli |
| Cold: all 50 Prelude modules + `Main` | 3.35 s |
| Re-check, nothing changed | 0.25 s (floor: reads and parses all sources, loads externs, checks timestamps) |
| Re-check, `Main` edited (8 lines / 38 lines, class, instance, records) | 0.34 to 0.44 s / 0.45 to 0.46 s |
| Re-check with a type error | 0.31 s, readable `TypesDoNotUnify` text |
| `WebAssembly.compile` / instantiate (Node) | about 35 ms / 11 ms |
| Memory | wasm linear memory about 19 to 21 MB; Node process 177 to 197 MB RSS |

**Caveats on the figures.** Measured under Node 24's WASI on a real disk, on an Apple-silicon Mac, not in a browser worker. The harness parses all Prelude sources every run; a purpose-built entry point that takes only externs would be faster. Only Prelude was loaded; real Solutions may import `arrays`, `maybe`, etc., which raise the externs and load time. Code generation to JavaScript ran (output written) but the generated JavaScript was not executed. Nothing run through `-N`/threads: the runtime is single-threaded.

**What had to be patched** (diff at [purescript.patch](https://github.com/jafonsor/purs-wasm/blob/main/nix/purescript/purescript.patch); runner [run.mjs](../research/10-purs-wasm/run.mjs); entry point [purs-core-Main.hs](https://github.com/jafonsor/purs-wasm/blob/main/nix/purescript/purs-core-Main.hs); [cabal.project](../research/10-purs-wasm/cabal.project)):
- Library trimmed to the compile pipeline: removed the `Ide`, `Interactive` and `Publish` modules (kept the two `Publish` helper modules the core uses) and the dependencies `network`, `haskeline`, `process`, `typed-process`, `monad-logger`, `conduit*`, `cryptonite`, `memory`. This removed the `network` and `basement` blockers from [research 07](../research/07-purs-browser-port.md) without porting them.
- `Make/Cache.hs`: content hash is now the raw file bytes (no SHA-512). Fine for an in-memory/one-shot build; the on-disk cache format changes.
- `cabal.project`: `shared: True` and `library-for-ghci: False` (Template Haskell on wasm loads dependencies as shared libraries; without it the build fails with missing `.dyn_hi`), `cborg` from git master, `allow-newer: all`, `cheapskate` with a `Control.Monad` import.
- `Parser.hs` was generated by a native `happy` (the wasm `happy` cannot run at build time); this patch does not include the generated file.
- A new executable `purs-core` (about 36 lines): parse files, `buildMakeActions`, `make`, print errors and elapsed time. A browser version replaces the disk with an in-memory filesystem or `MakeActions` fed externs bytes.

**What failed or is awkward.**
- `wasm32-wasi-cabal` can fail with "Version mismatch between ghc and ghc-pkg" after the plan changes; fix is to put a `ghc-pkg` symlink to `wasm32-wasi-ghc-pkg` first on `PATH`.
- GHC 9.8 and the `native` flavour are not obtainable on this machine (see above). Building on Linux x86_64 would offer them; not tried.
- Not done: a browser web worker run, an in-memory filesystem, executing the generated JavaScript, a multi-library externs set, `wasm-opt` size tuning, Nix packaging of the build.

**Effect on the map's fog.** The port is feasible, so the fallback fog is mostly settled (kept only for the browser test failing). Check latency, syntax errors and build/deploy can now be asked sharply; see the new tickets.
